# Техническая документация: RAAN/Phase-оптимизатор (`raan_optimizer.py`)

## Назначение

`raan_optimizer.py` — модуль автоматического подбора оптимальной ориентации орбитальных плоскостей. Решает задачу: **при фиксированном количестве спутников и плоскостей найти такие углы RAAN, которые максимизируют сквозную доступность для заданных наземных пунктов**.

## Проблема

RAAN (Right Ascension of Ascending Node) определяет, **как повёрнута** каждая орбитальная плоскость вокруг полярной оси Земли. Разные значения RAAN приводят к разному взаимному расположению «полос покрытия» от каждой плоскости.

Для 3 плоскостей пространство поиска — $360° \times 360° = 129{,}600$ комбинаций (при шаге 1°). Полный перебор с полной симуляцией каждого варианта потребует $129{,}600 \times 30$ с $\approx 45$ дней.

## Решение: Coarse-Grained Grid Search

### Архитектура

```
optimize_raan_phase(base_scenario, step_deg=30, top_n=5)
    │
    ├── fix P1 (RAAN=0, Phase=0)
    │
    ├── for dr2 in range(0, 180, 30):        # 6 значений
    │   └── for dr3 in range(0, 180, 30):    # 6 значений
    │       │
    │       ├── modify_planes(base, offsets)
    │       └── coarse_availability(modified_scenario, n_checks=8)
    │           │
    │           ├── for t_s in [0, 10800, 21600, ...]:  # 8 точек
    │           │   ├── geometry.snapshot(scenario, t_s)
    │           │   ├── nx.Graph() ← edges
    │           │   └── nx.has_path(client, gateway)
    │           │
    │           └── return connected_checks / total_checks
    │
    └── sort by score, return top_n
```

### `coarse_availability(scenario, n_checks=8) → float`

Быстрая оценка доступности без полной симуляции.

**Параметры:**
- `scenario` — сценарий с модифицированными RAAN/Phase
- `n_checks` — количество контрольных точек (по умолчанию 8)

**Алгоритм:**

1. Вычислить шаг: $\text{step} = \text{horizon} / n_{\text{checks}}$ (для 86400 с и 8 точек → шаг 10800 с = 3 часа).
2. Для каждой контрольной точки $t_s \in \{0, 10800, 21600, \ldots\}$:
   a. Получить snapshot и построить граф
   b. Для каждого клиента проверить:
      - Есть ли хотя бы один видимый активный спутник ($\varepsilon \geq \varepsilon_{\min}$)
      - Есть ли путь до хотя бы одного доступного шлюза (`nx.has_path`)
   c. Если оба условия выполнены → `connected_checks += 1`
3. Вернуть $\frac{\text{connected\_checks}}{\text{total\_checks}}$

**Сложность:** $O(n_{\text{checks}} \times N^2)$ на один вызов. При $n_{\text{checks}} = 8$ и $N = 48$: ~8 × 2304 = 18432 операций — менее 10 мс.

### `modify_planes(base_scenario, raan_offsets, phase_offsets) → dict`

Создаёт глубокую копию сценария с модифицированными углами:

$$\text{RAAN}_i' = (\text{RAAN}_i + \Delta\text{RAAN}_i) \bmod 360°$$

$$\text{Phase}_i' = (\text{Phase}_i + \Delta\text{Phase}_i) \bmod 360°$$

### `optimize_raan_phase(base_scenario, step_deg=30, top_n=5) → list`

**Стратегия поиска:**

1. **P1 фиксирована** (RAAN = 0°): система координат определяется первой плоскостью.
2. **P2 и P3 варьируются** по RAAN в диапазоне [0°, 180°) с шагом `step_deg`.
   - Диапазон [0°, 180°) вместо [0°, 360°) — из-за зеркальной симметрии: поворот на 180° даёт зеркальную конфигурацию с идентичной доступностью для северных пунктов.
3. **Phase фиксирован** (0°) для скорости.

**Количество вычислений:**

При `step_deg = 30`:
- 6 значений для P2 × 6 значений для P3 = 36 комбинаций
- 36 × 8 snapshot'ов = 288 вычислений
- Время: ~2–5 секунд

**Выходные данные:**

```python
[
    (0.92, scenario_with_raan_60_120),    # Лучший
    (0.89, scenario_with_raan_90_150),    # 2-й
    (0.87, scenario_with_raan_30_90),     # 3-й
    ...
]
```

## Почему не полнопространственный поиск

| Подход | Комбинаций | Время | Качество |
|--------|-----------|-------|----------|
| 1° grid, полная симуляция | 129,600 | ~45 дней | Идеальное |
| 1° grid, coarse-grained | 129,600 | ~22 мин | Хорошее |
| 30° grid, coarse-grained | 36 | ~3 с | Достаточное |
| 30° grid + local refinement 5° | 36 + ~50 | ~8 с | Высокое |

Мы выбрали вариант **30° grid, coarse-grained** — он даёт результат за секунды и находит конфигурации с доступностью, близкой к оптимальной (ошибка <3–5%).

## Ограничения и возможные улучшения

1. **Phase не оптимизируется** — сейчас зафиксирован на 0°. Добавление phase-поиска увеличит пространство в 6× (6 значений phase для каждой плоскости), но может улучшить результат на 1–3%.

2. **Нет local refinement** — после нахождения лучшего 30°-кандидата можно выполнить уточняющий поиск с шагом 5° в окрестности ±15°. Это даст +~1% доступности за дополнительные ~2 секунды.

3. **Не учитывает failures** — оптимизация выполняется для штатного режима. Для робастной оптимизации нужно считать `coarse_availability` по нескольким сценариям отказов.
